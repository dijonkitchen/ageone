# SPEC-0006: Algorithm Roguelike

## Functional requirements

A turn-based, grid-based roguelike where learning an algorithm or data structure unlocks it in the game.
The game starts small and simple, and each concept the player learns makes the game itself bigger and deeper.

### Core loop

1. The player explores a dungeon floor, fights, and collects loot.
2. They find a **codex page** (a locked concept, such as BFS) whose effect they can see but can't use yet.
3. At a **shrine** (a safe room) they unlock it through a **lesson**: an explanation, a step-through visualization, and a **trial** that checks understanding.
4. Once unlocked, the concept becomes an ability, a game system, or a generator, and later floors are built to need it.

The concepts work as the skill tree.
A concept needs its prerequisites unlocked first (union-find before Kruskal, for example), so the codex is a dependency graph the player can see.

### Trials

Each trial has two modes; passing either one unlocks the concept.

- **Puzzle mode** (default, no coding): the player plays the algorithm by hand inside the game.
  For example, they pick which node BFS visits next, place cuts for a BSP split, or pop the right heap entry.
  The game checks each step against a reference implementation and shows where the player went wrong.
- **Code mode** (opt-in): the player writes the function in an in-game editor against a small, documented interface.
  A test suite and a performance budget grade it.
  When it passes, **the player's own code runs that part of the game** from then on, and they can switch back to the reference implementation at any time.
  Code mode is sandboxed, so player code can't reach anything outside the game state it is given.

### Concepts and what they unlock

The first release covers the tiers below, in this order of difficulty.
Each concept lists the in-game effect that makes learning it worth it.

| Tier | Concept | Unlocks in the game |
|------|---------|---------------------|
| 1 | Arrays and 2D grids | The map itself; the starting floor is a single hand-made room |
| 1 | Stack | Undo the last move once per floor; backtracking out of dead ends |
| 1 | Queue and BFS | Flood-fill reveal: see the whole room you are standing in |
| 1 | Hash map | Inventory with stacking and quick lookup by name |
| 1 | Seeded PRNG | Daily seeded runs and replays shareable by seed |
| 2 | DFS and random walk | Cave floors generated by drunkard's walk |
| 2 | Bresenham lines | Thrown items and ranged attacks with line of sight |
| 2 | Recursive shadowcasting | Proper field of view and fog of war |
| 2 | Priority queue (binary heap) | Speed-based turn scheduler: fast and slow monsters, haste and slow effects |
| 2 | Dijkstra | Dijkstra maps: monsters that chase, flee, and surround |
| 2 | Weighted random (alias method) | Loot tables and rarity tiers |
| 3 | BSP tree | Room-and-corridor floors |
| 3 | Union-find | Guaranteed-connected floors and locked-door puzzles |
| 3 | Minimum spanning tree (Kruskal) | Corridors that join rooms with loops added back for variety |
| 3 | A* | Auto-travel to any explored tile, and smarter monsters |
| 3 | Finite state machine | Monster behaviors: patrol, alert, hunt, flee |
| 3 | Cellular automata | Organic caverns, spreading fire, and gas |
| 4 | Topological sort | Crafting recipes and multi-step quests |
| 4 | Behavior tree | Boss AI with phases |
| 4 | Trie | Spell incantations typed by prefix |
| 4 | Wave Function Collapse | Themed floors from tile rules |
| 4 | Minimax with alpha-beta | Duels against a rival who plans ahead |

Floors use only generators and systems the player has unlocked, plus the one being taught next, so the dungeon visibly grows with the player.

### Game

- Classic roguelike rules: turn-based, grid movement, permadeath, procedurally generated floors.
- Meta-progression: unlocked concepts persist across runs; items and floor depth don't.
- A **sandbox** mode lets the player run any unlocked algorithm on any map, step by step, with speed controls and a view of its data structures (the queue, heap, visited set, union-find forest).
- Each unlocked concept shows its time and space complexity and a link to a further reading source.

## Non-functional requirements

- Simple to start: runs in a web browser with nothing to install, and plays with keyboard alone.
  Tile graphics are optional; the game is fully playable as ASCII.
- Deterministic: the same seed and inputs give the same run, so runs can be replayed, shared, and tested.
- Correct: every reference implementation has unit tests, and every puzzle-mode trial is checked against its reference.
  The test suite a code-mode trial grades against is the same one the reference passes.
- Safe: code-mode player code runs in an isolated sandbox with a time and memory limit and no network or storage access.
  A player's code that crashes or times out falls back to the reference and never ends a run.
- Approachable: lessons assume only basic programming; each lesson takes about 5 to 15 minutes.
  Puzzle mode needs no coding, so non-programmers can play.
- Accessible: colorblind-safe palette, adjustable text size, and no reliance on color alone.
- Extensible: adding a concept is adding a folder (lesson text, reference implementation, tests, puzzle definition, and its in-game hook), with no change to the engine core.
- Language and engine choices (for example TypeScript in the browser, and which code-mode language to support) are recorded in a decision record before building.

## Definition of done

1. A decision record covers the language, rendering, and code-mode sandbox choices.
2. The game runs in a browser from one command, and a CI job builds and tests it on every pull request.
3. All tier 1 and tier 2 concepts are playable end to end: codex page, lesson, puzzle-mode trial, and the unlocked effect in game.
4. At least three concepts (including BFS and the priority queue) also have a code-mode trial whose passing code runs in the game.
5. Floors grow with unlocks: a new player starts in a single room, and a player with tier 2 unlocked gets cave floors with fog of war and speed-based turns.
6. Given a seed and an input log, a run replays identically, checked by a test.
7. Each reference implementation has unit tests, and adding a new concept is documented and needs no engine change.
